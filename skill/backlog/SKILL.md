# Беклог задач

Задачи — md-файлы в `~/backlog/<проект>/<ID>.md` (каталог переопределяется `BACKLOG_DIR`). Создание,
взятие в работу и смена статуса — только через CLI `backlog`: он выдаёт ID без коллизий, проверяет связи
и находит проект по текущему репозиторию. Файлы задач вручную не создавай и не переименовывай.

Если `backlog` не найден (`command not found`) — файлы сам не пиши. Скажи пользователю: «CLI backlog
не установлен: выполните `npm i -g p-backlog`».

## Записать задачу

Записывай сам, не спрашивая пользователя, если замечание одновременно:

- **вне рамок** текущей работы — его исправление не входит в то, о чём просили;
- **конкретно** — есть `файл:строка` и понятно, что сломается или чем это грозит;
- **не чинится попутно**:
  - то, что не меняет поведение и лежит в коде, который ты и так меняешь (опечатка, неиспользуемый импорт,
    неточное имя), — просто исправь;
  - баг, из-за которого код работает неправильно, — отдельная задача, даже если исправление в одну строку
    и в том же файле: об изменении этого поведения не просили;
  - если без исправления бага текущую задачу не сделать — исправь его в рамках задачи и прямо напиши
    в ответе, какое поведение изменил и где (`файл:строка`).

Не записывай: вкусовые замечания без последствий, непроверенные догадки, то, что чинишь в этой же задаче.

1. Проверь дубли по 2–3 ключевым словам сути проблемы:
   ```bash
   backlog list --query "таймаут загрузк"
   ```
   Есть открытая задача про то же — новую не создавай, упомяни существующий ID в итоговом ответе.

2. Создай задачу. Описание передавай всегда через heredoc — без него команда ждёт stdin:
   ```bash
   backlog new --title "Таймаут загрузки не учитывает размер файла" \
     --priority high --tags upload,network --source src/upload/client.ts:88 --category bug <<'EOF'
   Таймаут фиксированный — 30 с, файлы больше ~500 МБ обрываются на медленном канале.

   **Чем грозит:** большие файлы не загружаются, повторная попытка тоже падает.

   **Как проверить:** загрузить файл 2 ГБ при троттлинге сети «Slow 3G» в DevTools.

   ## Чеклист
   - [ ] Считать таймаут от размера файла
   - [ ] Тест на расчёт таймаута
   EOF
   ```
   - `--title` — суть проблемы, а не действие: «Таймаут загрузки не учитывает размер файла», а не «Поправить таймаут».
   - `--priority`: `critical` — ломает прод или данные; `high` — заметный пользователю баг; `medium` — долг, который мешает работе; `low` — улучшение.
   - `--tags` — область кода и вид работы: `upload`, `auth`, `tech-debt`, `tests`.
   - `--source` — где заметил, `файл:строка`.
   - `--category` — обязательно. Запах кода — его категория из каталога code-smells: `bloaters`,
     `change-preventers`, `couplers`, `data-dealers`, `dispensables`, `functional-abusers`,
     `lexical-abusers`, `oo-abusers`, `obfuscators`. Неправильное поведение — `bug`.
   - `--found review` — находка аудита или ревью по просьбе пользователя; замеченное попутно флага не
     требует.
   - Работаешь над задачей из беклога — добавь `--related <её ID>`.
   - Чеклист — проверяемые шаги: по нему считается прогресс.
   - Код выхода 3 и «Похоже на SPA-12 — …» — такая задача уже открыта: новую не создавай, упомяни
     существующий ID в ответе. `--force` — только если это точно другая проблема.
   - Несколько мелких находок одного ревью (уровня Minor: запахи, мелкие неточности) — **одной** задачей, а не
     каждой отдельно: заголовок «Мелочи ревью: <что ревьюили>», в чеклисте по пункту на находку
     (`- [ ] Magic Number — src/a.ts:42: что не так`), `--category` — самая частая категория среди находок,
     `--source` — место первой. Отдельными задачами — только важные находки и баги.

3. В конце ответа перечисли созданное отдельным блоком, который начинается строкой «Добавлено в беклог:» —
   по ней пользователь находит новые задачи в длинном ответе:
   ```
   Добавлено в беклог:
   - SPA-14 — Таймаут загрузки не учитывает размер файла
   ```
   Если CLI написал «Создан проект …» — добавь это одной строкой.

Несколько задач про одно — собрать их в эпик: создать эпик (`backlog new --type epic --title …`) и перенести
задачи `backlog epic <ID> [<ID> …] --to <ID эпика>`; `--to none` вынимает задачу из эпика. Эпик закрывается
сам, когда закрыты все его задачи.

## Взять задачу в работу

«Возьми SPA-12» → `backlog take SPA-12`. «Возьми следующую» → `backlog take --next` (проект — по текущему
репозиторию; из другого каталога добавь `--project <id>`). «Возьми все задачи по src/web/stats» →
`backlog take --path src/web/stats`: берёт все открытые задачи, чей `source` внутри пути (заблокированные
пропускает), и печатает их подряд через `---` (с `--json` — одним JSON-массивом) — исправляй их вместе,
закрывай каждую.

| Код | Что случилось | Что делать |
|---|---|---|
| 0 | Статус стал `in-progress`, выведены путь, связи и текст задачи | Работать |
| 1 | Это эпик | Показать пользователю задачи эпика из вывода и спросить, какую взять |
| 2 | Задача или проект не найдены, открытых задач нет | Сообщить пользователю |
| 3 | Открытые блокеры или задача уже закрыта; при `--next` и `--path` — все подходящие задачи заблокированы | Перечислить блокеры и остановиться. `--force` — только по прямой просьбе пользователя |

1. Прочитай описание и `source`; нужные связанные задачи — `backlog show <ID>`.
2. Делай работу. Выполнил пункт чеклиста — сразу отметь его в файле задачи (`- [ ]` → `- [x]`, путь есть
   в выводе `take`). Появились новые шаги — допиши их в чеклист. Frontmatter руками не меняй.
3. Посторонние проблемы, найденные по ходу, — через «Записать задачу» с `--related <ID>`.
4. Перед закрытием проверь результат командами проекта: тесты, линт, типы.
5. Всё сделано, проверено и закоммичено → `backlog close <ID> --as fixed --reason "Исправлено в <sha>: <что
   именно>"` — по хешу статистика узнаёт, кто и чем исправил. Коммита нет (правки ещё не закоммичены) →
   `backlog status <ID> done`. Если CLI предупредил о неотмеченных пунктах —
   отметь сделанные; если что-то не сделано, задача не закончена.
6. Сделано не всё → статус оставь `in-progress`, допиши в конец файла задачи раздел и скажи пользователю,
   что осталось:
   ```markdown
   ## Заметки
   - <сегодняшняя дата>: сделано …; осталось …, потому что …
   ```

## Перепроверить задачи

Когда: сообщение хука «после последней проверки менялся код задач», просьба «проверь беклог» или
«почисти беклог».

1. `backlog check --json` из репозитория проекта (из другого каталога — `--project <id>`). Висячие ссылки,
   завершённые эпики и сдвинутые `source` он уже исправил сам — это поле `fixed`, список `{ kind, taskId, … }`:
   `references-removed` — убраны ссылки на несуществующие задачи `ids`; `epic-closed` — эпик закрыт, все его
   задачи `childIds` закрыты; `source-moved` — `source` сдвинулся `from` → `to`. Перескажи его пользователю
   одной строкой. Код выхода 5 — не сбой: есть кандидаты или проблемы задач, которые надо разобрать; 0 —
   разбирать нечего.
2. У кандидата `source-changed` в JSON уже есть `problem` — первый абзац описания задачи, `snippet` —
   текущий код вокруг `source` с номерами строк — и `diff` — изменения файла с последней проверки (у
   обрезанного `diffOmittedLines` — сколько строк не показано). Обычно этого хватает: реши по ним, не вызывая
   `show`, `grep` и `git show`. Читай задачу (`backlog show <ID>`) и код целиком,
   только если по `snippet` и `diff` не понять; у `duplicate` и `source-missing` читай задачи всегда.
   Если у кандидата есть поле `source` — строки задачи сдвинулись, это её место в текущем файле, и `snippet`
   показан по нему. Подтверждаешь проблему — `backlog verify <ID> --source <этот source>`.
3. Реши:

   | Что видно в коде | Команда |
   |---|---|
   | Описанной проблемы больше нет | `backlog close <ID> --as fixed --reason "Исправлено в <sha>: <что именно>"` (без хеша существующего коммита CLI не закроет) |
   | Кода или фичи, о которых задача, больше нет | `backlog close <ID> --as obsolete --reason "<что удалено и где>"` |
   | `source-missing`: код переехал (подсказка — `renamedTo`), проблема на месте | `backlog verify <ID> --source <новый файл:строка>` |
   | `source-missing`: кода, о котором задача, больше нет | `backlog close <ID> --as obsolete --reason "<что удалено и где>"` |
   | `duplicate`: две задачи про одно | закрой менее полную: `backlog close <ID> --as duplicate --duplicate-of <другая> --reason "<в чём совпадают>"` |
   | `duplicate`: задачи про разное | подтверди обе: `backlog verify <ID>` и `backlog verify <другая>` |
   | Проблема на месте, но код сдвинулся | `backlog verify <ID> --source <файл:строка>` |
   | Проблема на месте или уверенности нет | `backlog verify <ID>`; несколько сразу — `backlog verify <ID> <ID> …` |

   Простой `backlog verify <ID>` не снимает `source-missing`: пропавший файл уходит из кандидатов только
   с новым `--source` или закрытием, иначе хук будет напоминать о задаче после каждого ответа. Не нашёл,
   куда делся код, — спроси пользователя. Пара `duplicate` уходит, только когда подтверждены обе задачи.

   Закрывай только с конкретной уликой: коммит, строка, факт отсутствия кода. «Похоже, уже неактуально» —
   не улика: подтверди задачу и оставь открытой. Закрытая задача через 7 дней удаляется вместе с файлом.

4. `problems` — список `{ kind, … }`. `file-not-parsed`: файл `path` не разбирается, причины в `problems` —
   поправь YAML руками, не меняя `id`. Остальное перечисли пользователю: `task-invalid` (ошибка `problem`
   в задаче `taskId`), `fix-failed` (исправление не записалось, причина `cause`), `epics-wait-for-files`,
   `project-without-repos`, `project-repos-missing`, `project-repo-not-git`, `project-history-unreadable`,
   `prefix-shared` (у проектов `projectIds` один префикс — ID задач пересекаются).
5. В конце ответа — блок, по которому пользователь найдёт закрытое:
   ```
   Закрыто в беклоге:
   - SPA-14 — Таймаут загрузки не учитывает размер файла: исправлено в a1b2c3d
   ```
   Подтверждённые задачи не перечисляй, достаточно «Остальные задачи подтверждены».

Если перепроверку запросил хук, после неё просто закончи ответ: второй раз подряд хук не срабатывает.

## Разобрать застоявшиеся мелочи

Когда: тревога «Задач с низким приоритетом старше 30 дней» или просьба «разбери старые задачи».

1. `backlog prune` — список задач с низким приоритетом старше 30 дней, которые не брали в работу. Ничего
   не меняет.
2. Покажи список пользователю и спроси, отменить ли их. Нужные задачи он может поднять в приоритете или
   взять в работу.
3. Только после явного согласия — `backlog prune --apply`: отменяет их как `obsolete`.

## Посмотреть беклог

Проект, который больше не ведётся, помечается неактивным: `backlog project status <id> inactive` — его
задачи выпадают из общей области «Проекты» (список и статистика), но остаются доступны на странице проекта.
`backlog project list` показывает статусы. Удаление проекта (`backlog project delete <id> --confirm <id>`)
сносит каталог со всеми задачами — выполнять только по прямой просьбе пользователя.

«Что в беклоге» → `backlog list`: открытые задачи текущего проекта по приоритету. По запросу:
`--all-projects`, `--status done`, `--tag <тег>`, `--query <текст>`. Подробности — `backlog show <ID>`.

Сводка и тревоги — `backlog stats`.

Сменить категорию — `backlog category <ID> <категория|none>`. Сменить приоритет — `backlog priority <ID> <low|medium|high|critical>`.
